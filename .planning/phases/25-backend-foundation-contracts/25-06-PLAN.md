A. `apps/mobile/scripts/smoke-api.mjs <baseUrl> [--mode=preview|prod|disabled] [--no-burst]` (Node 22 global fetch, ESM, no dependencies; default mode preview). It builds valid payloads inline: crypto.randomUUID ids, a fixed 64-hex contentHash, 2 seats, 3 outcomes, status finished, winnerSeat 0, schemaVersion 1, plus a valid feedback with questionSnapshot. Each check prints `PASS|FAIL <name> (<status>)` and the script exits 1 if any check fails.

Checks in both modes:
- GET /api/v2/health returns 200 JSON status ok.
- GET /api/v1/packs.json returns 200 with application/json.
- GET /game/setup returns 200 text/html.
- GET /statusz returns 200 JSON with a `backend.db.status` field.
- GET /statusz.json returns 200 JSON.
- GET /api/v2/games returns 405 or 404 and is not text/html.
- POST /api/v2/games with an unknown field returns 400 `invalid_request`.
- POST /api/v2/games with a 70 KB body returns 413.
- POST /api/v2/feedback with reason other and no note returns 400.
- Unless --no-burst: 80 rapid POSTs of `{}` to /api/v2/games show at least one 429 (D-07; lag up to 10 s tolerated).

Preview-only writes:
- POST a valid game returns 201; the identical repeat returns 200 with an identical body text.
- POST a valid feedback returns 201; the repeat returns 200 identical.
- Print the created gameId and feedbackId as `SMOKE_GAME_ID=<uuid>` / `SMOKE_FEEDBACK_ID=<uuid>` lines, so 25-08/25-09 can query the DB branch for them.

Disabled mode (for deploys where D-15 set TW_BACKEND_DB_DISABLED=1): health is expected to return 503 with db.status down, /statusz backend.db.status to equal `disabled`, and one valid game POST to return 503 `backend_disabled`; all other checks are as in prod mode. Production mode never sends a valid (writable) payload, so no test data is written to production. If 429 trips early, wait 65 s before the write checks: run the burst LAST.
